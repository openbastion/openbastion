# ADR-0131 — L'Admin UI s'adapte aux capacités que les politiques ouvrent à l'appelant

**Statut** `Accepté` · 2026-11-20 · go du propriétaire du projet le 2026-11-20 : « Route de capacités » et règle d'affichage « Mixte », choisies parmi les options proposées.

**Contexte** — L'Admin UI montrait toutes les pages et toutes les actions à tout utilisateur connecté : un opérateur voyait « Enregistrer un compte », « Renouveler le secret », « Créer une politique » ou « Approuver », et ne découvrait son absence de droit qu'au refus du serveur (`403`). Les droits ne sont pas des rôles figés : ce sont des politiques dynamiques (rôle → motif de ressource → motif d'action → effet, ADR-0114), évaluées par le service Authorization ressource par ressource (`vault:account-admin:<id>`, `session-approve:account:<id>`, `recording:session:<id>`…). Aucune route publique ne disait à l'interface ce que l'appelant peut faire ; le jeton ne porte que des rôles.

**Décision**

1. **Authorization** expose `POST /authz/v1/capabilities` (mTLS, appelant **`api-gateway` seul**) : une liste de 1 à 32 questions `{resource, action, prefix}`, évaluées sur **une seule** lecture des politiques des rôles fournis, réponse `{"allowed": [bool…]}` dans l'ordre, `Cache-Control: no-store`, sans raison ni politique. Une question exacte est la règle de `CheckAccess` (factorisée, inchangée) ; une question `prefix` demande si l'action est permise sur **au moins une** ressource dont le nom commence par le préfixe (`domain.AllowsSomeUnder`) : vrai si une politique `allow` pour l'action peut toucher une ressource du préfixe, faux si une politique `deny` pour l'action couvre tout le préfixe (joker final dont le préfixe part), faux par défaut. Corps ≤ 32 Kio, champs inconnus refusés, ressource et action de 1 à 256 octets : sinon `400` ; magasin en panne : `503` qui ne nomme rien.
2. **La Gateway** expose `GET /auth/me/capabilities` (jeton requis, aucun paramètre, `Cache-Control: no-store`) et porte le **catalogue fermé** des capacités de l'interface, chacune liée aux ressources et actions que les services vérifient réellement : `accounts.list` (`vault:account-admin:*`, `vault:account:list`, exact), `accounts.onboard|rotate|disable|pin|approval` (préfixe `vault:account-admin:`), `policies.create` (`authz:policy-admin`, exact), `sessions.create` (`vault:account:`), `sessions.breakglass`, `sessions.approve` (`session-approve:account:` **ou** `breakglass-approve:account:`), `sessions.read`, `sessions.terminate`, `secrets.inject`, `recordings.read` (`recording:session:`), `audit.secretInjections` (exact). Les rôles sont ceux du jeton vérifié, jamais ceux de la requête. Authorization injoignable, refus mTLS ou nombre de réponses différent du nombre de questions : `503`.
3. **L'Admin UI** lit les capacités une fois par jeton et applique la règle **mixte** :
   - une page ou un onglet qui ne sert que des capacités dont l'appelant n'a aucune est **absent** (navigation, palette de commandes, raccourcis) : `Accès privilégiés` (aucune de `accounts.list`, `accounts.onboard`, `policies.create`, `sessions.approve`), `Sécurité` (sans `accounts.list`), les onglets `Ressources`/`Comptes`, `Politiques`, `Demandes` d'Accès privilégiés, l'onglet `Enregistrements` de Sessions, le rapprochement des injections ;
   - dans une page visible, une action non autorisée est **grisée**, avec ce qu'elle requiert (« Requiert le droit : … ») : enregistrer, épingler, exiger l'approbation, renouveler, désactiver un compte ; nouvelle demande ; approuver et refuser ; saisir le secret Vault ; mettre fin à la session d'un autre. Le demandeur garde « Mettre fin » sur sa propre session (ADR-0017) et lui seul peut « Ouvrir l'écran » (`POST /connect`).
   - Les lectures interdites ne sont plus demandées (inventaire du coffre sans `accounts.list`).
4. **Fermé pour les actions, ouvert pour les pages, quand on ne sait pas** : tant que les capacités chargent, ou si elles n'ont pas pu être lues, toute action conditionnée est grisée ; les pages restent visibles (leurs lectures sont refusées par le serveur) et un bandeau dit que les droits n'ont pas pu être chargés.
5. **La Gateway pose ses propres décisions par la même route.** `GET /audit/secret-injections` demandait `check-access`, que la règle mTLS d'Authorization refuse à la Gateway : sous mTLS, la route répondait `503` à tous. Elle pose désormais la question exacte (`audit:secret-injections:all`, `audit:secret-injections:read`) par `POST /authz/v1/capabilities` (`askCapabilities`, commun aux deux routes) ; `check-access` reste fermé à la Gateway. Complément du 2026-11-20.
6. **Ce n'est jamais une autorisation.** Chaque route reste décidée par Authorization sur sa propre ressource ; une capacité vraie peut être refusée sur une ressource précise (une politique sur un seul compte rend `accounts.rotate` vrai). Masquer n'est pas une défense : un client qui ignore l'interface reçoit les mêmes refus qu'avant.

**Conséquences**

- (+) Mesuré : `AllowsSomeUnder` 14 cas (dont les refus qui couvrent le préfixe et ceux qui ne le couvrent pas) ; `Capabilities` (ordre, bornes, magasin en panne) ; route HTTP (`400` ×5, `503` sans détail, `405`) ; règle mTLS (Gateway seule) ; Gateway (rôles du jeton, catalogue, `401`/`400`/`405`, `503` ×4) ; Admin UI 7 tests (navigation, palette, bandeau, onglets, actions grisées, demandeur) ; huit processus réels sous mTLS : administrateur, opérateur sur un compte et auditeur reçoivent chacun leurs capacités, le Command Recorder qui demande est refusé (`403`).
- (+) Contre-épreuves : réponse acceptée avec un booléen de trop, rôle ajouté à ceux du jeton, `can()` toujours vrai, pages toujours affichées, Gateway retirée des appelants d'Authorization (`503` sur processus réels) — chacune fait échouer ses tests.
- (−) Une capacité est un **majorant** : un refus explicite compte par compte sur toutes les ressources autorisées n'est pas vu, l'action reste active et le serveur la refuse (comportement d'avant).
- (−) Les capacités sont lues **une fois par jeton** : une politique créée ou retirée pendant la session n'est vue qu'à la connexion suivante.
- (−) Le catalogue est maintenu à la main dans la Gateway : une nouvelle vérification d'un service sans capacité correspondante reste visible et active dans l'interface. Les tests vérifient les questions posées, pas l'exhaustivité.
- (−) Un bouton grisé porte son explication dans `title` et `aria-description` ; le bouton désactivé n'est pas focalisable au clavier.
- (−) Ajoute une route interne et une route publique ; aucun contrat existant n'est rompu.

**Alternatives envisagées**

- **Table rôles → fonctions dans l'interface** : rapide, sans serveur, mais fausse dès qu'une politique ouvre un droit à un autre rôle — des fonctions autorisées seraient masquées. Écartée par le propriétaire.
- **Apprendre des refus** (tout afficher, griser après un `403`) : aucun changement serveur, mais l'utilisateur découvre ses limites en échouant, et chaque refus d'audit compte. Écartée.
- **Ouvrir `check-access` à la Gateway et poser les questions une par une** : 16 allers-retours mTLS par connexion, et `check-access` ne sait répondre que sur une ressource exacte — une politique sur un seul compte serait invisible. Écartée.
- **Exposer les politiques de l'appelant** : révèle la configuration de contrôle d'accès au navigateur. Écartée.
